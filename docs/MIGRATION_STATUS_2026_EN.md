## 2. Key verification

- The line pool was generated by the official Java `LinePoolGenerator` (JDK 21, no CPLEX needed), **93** lines in total. In addition, an independently written Python enumerator (only a test oracle, not a production generator) enumerated from scratch by the rules and obtained exactly the same set (0 missing, 0 extra).
- For each line, the duration, `c^V=(2·duration+60)/60`, the maximum frequency (minimum over the connections traversed), reverse service (reverse connections in reverse order), forbidden turns, simple path, terminals and detour ≤ 1.1 were all re-checked by Python and pass.
- The DPTN shortest times exported by the official route generator agree with the Python route pool; all 416 ODs have routes, and no OD was dropped.
- The line pool and routes regenerated by Java are byte-for-byte equal to the frozen files (the test runs when JDK 21 is available).
- $M$: $\max\underline c_{od}=80.4284615$ (Ddr–Lls) → $M=\lceil 3\times 80.4284615\rceil=242$; factors 2 and 5 correspond to 161 and 403. The maximum cost over all frequency-specific trips is **179.09 < 242** (all segments at frequency 1).
- Specification model vs. line-level form: objective values agree on 15 random tiny instances, the worked example, 5/10-OD subsets of Randstad-IC, and the final reduced experiment (difference $2\times10^{-8}$); the specification model itself was additionally checked against exhaustive enumeration one by one.

## 4. Experimental results

### 4.1 Reduced instance (**not** the main experiment)

The 10 largest ODs (18.6% of total demand), frequencies restricted to 1–4, budget scaled by demand share to $B_1=B_2=11.2$ (`60×0.186`).
This is a separately labelled scaled-budget experiment per §5.6 of the handoff document; the result JSON has `reduced_instance=true` and `budget_is_primary_60=false`.

Two periods, $M\times K$ (all optimal, gap 0):

| M | K | Objective | Service rate (period 1, period 2) |
|---|---|---|---|
| 161 | 0 / 10 / 1000 | 1,675,613.5 (identical for all three) | 0.6828, 0.6679 |
| 242 | 0 | 2,155,911.2 | 0.6828, 0.6679 |
| 242 | 10 / 1000 | 2,154,830.4 | 0.7077, 0.6679 |
| 403 | 0 | 3,081,009.5 | 0.7077, 0.6804 |
| 403 | 10 / 1000 | 3,080,117.3 | 0.7077, 0.6679 |

- Objective, service rate and the selected line frequencies all change with $M$ (when demand cannot be fully served, $M$ matters); $K=0$ gives a slightly higher objective than $K\ge10$.
- The pre-fixed intermediate value $K=10$ is **already non-binding** on this instance (same as $K=1000$), so in effect only $K=0$ and $K\ge10$ were distinguished. For a finer $K$ curve, values smaller than 10 should be added.
- Single-period consistency: with identical demand, the objective for $|\mathcal T|=2$ ($K=0$ and $K=1000$) is exactly twice that for $|\mathcal T|=1$ (2,598,832.88 = 2×1,299,416.44).
- 3-period robustness ($M=242$): objective 2,950,577.2 for $K=0$, and 2,916,557.7 for $K=10,1000$, all optimal.

### 4.2 Full Randstad-IC

Line-level form, 416 ODs, full frequency set, $B_1=B_2=60$, $M=242$, $K=10$, HiGHS (SciPy), 2 cores, 8 GB, 900-second limit:
**no solution better than "all unserved" (objective 23,852,403.5) was found, lower bound 12,672, gap 99.9%**. The full instance was therefore not solved, and no optimality conclusion for the full instance can be reported.
Side observations (exploratory single runs, logs not versioned): budget 60, 40 largest ODs, full frequency set: gap about 40% after 300 seconds; budget 60, 40 largest ODs, frequencies 1–4: gap about 61% after 240 seconds; scaled budget (16.8), 20 largest ODs, frequencies 1–4: gap about 10% after 200 seconds.

## 5. Deviations from, and errata to, the handoff document

1. **"Maximum line duration 60 minutes" is inaccurate**: the second line, 60, of `LineGeneration/small.txt` limits only Sprinter lines (`satisfiesSprinterDuration`). Randstad-IC has only Intercity, and the actual longest line is 101.49 minutes. The line pool is still the 93 lines output by the official generator.
2. **The "shortest realizable route" is computed relative to the frozen line pool**: for 50 ODs the shortest realizable route is longer than the infrastructure shortest route, by up to 17.63 minutes. The official +15 window is therefore not enough, so route export uses a +45-minute window, and Python then filters "shortest realizable + 15"; the code checks whether the window is sufficient (none insufficient in this instance).
3. **Removal of dominated same-line transfer itineraries** (5,244): if two adjacent segments on the same line are still served by that line after merging, the transfer version is necessarily worse than the no-transfer version, and removing it does not change the optimal value. The switch is `prune_same_line_transfers`.
4. **Line-level form**: an equivalent way of writing the model for solving, added to avoid the Cartesian expansion. The specification model (frequency-specific trips) is unchanged and remains the definition of the formulation.
5. The column meanings of `stations.txt` follow Java `Reader.readStation` (`terminalIC terminalSPR type inRandstad lat lon`), which differ from the column names in the official README. `allowedTypeChanges.txt` contains two irrelevant lines in Randstad-IC and is not used by an IC-only network.
6. The train frequency options are $\mathcal F_\ell=\{1,\dots,\bar f_\ell\}$ with $\bar f_\ell=\min_{e\in\ell}\mathrm{maxFrequency}_e$ (values 2, 10 or 20).

## 6. Unfinished work and known limitations

- **The MILP of the full Randstad-IC is unsolved** (see 4.2). The cause is that the linear relaxation is very weak (budget and the binary variables for opening lines), not the size: the line-level form has only 257 thousand variables. Directions to consider: stronger valid inequalities, Benders/column generation, a stronger solver (Gurobi/CPLEX/HiGHS with long runs + warm start), or, with your approval, restricting the frequency set/number of transfers.
- The reduced experiments contain only 10 ODs and use a scaled budget; they cannot be taken as a conclusion about the full Randstad-IC.
- The 3-period robustness experiment has been done only on the reduced instance.
- The official Java generator needs JDK 21 (the `java` on your computer is 11). It is needed only when regenerating the frozen data; daily runs and tests do not need Java.
- The old code was **not deleted**: `passenger_line_planning/`, `datasets/passenger-toy/`, `results/passenger_toy/`, `multi_period_line_planning/` and the Germany-rail-related content are still there. The deletion threshold of §9.2 (loader, 93-line pool verification, route tests, minimal MILP test) is now met; whether and when to delete is up to your confirmation. `docs/PASSENGER_MODEL_IMPLEMENTATION.md` describes the old Bahn version and has been superseded by `docs/BENCHMARK_2026_IMPLEMENTATION.md`.
